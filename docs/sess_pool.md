# CPU 参与推理：n×GPU + m×CPU 异构 session 池

> 用户的观察：导出时 CPU 只有 43%、GPU 82%，想「多开几个 CPU EP 的 session 榨干空闲 CPU」。
> 结论先说：**在这台机器上没净收益（<5%），自动档默认只开 1 份 GPU session**；而且不是
> 因为「CPU 单张 615 ms 太慢」——是因为**这一段的 48 ms 里只有 8 ms 是网络**，
> 剩下 40 ms 是 CPU 侧的 letterbox resize + 争用，多开 session 只是把同一份 CPU 活
> 做两遍。数据在下面。

## 1. 按模型：GPU EP vs CPU EP（`app/tools/bench/sess_bench.py`）

单张中位 ms（同一份 onnx，只换 EP；本机 16 物理核 / 32 逻辑核，RTX 5070 Laptop）：

| 模型 | 输入 | GPU EP | CPU EP | CPU/GPU | 一份 CPU session 的内存 |
|---|---|---|---|---|---|
| dfm 384（张元英.dfm） | 1×384×384×3 | **37.19** | **494.48** | 13.3× | **2676 MB** |
| retinaface_10g | 1×3×640×640 | 8.75 | 53.65 | 6.1× | ~1041 MB |
| xseglite（256） | 1×3×256×256 | 3.90 | 42.97 | 11.0× | ~157 MB |
| tinymog | 1×3×640×640 | 4.23 | 4.35 | **1.0×** | ~40 MB |
| insightface_2d106 | 1×3×192×192 | 1.82 | 3.94 | 2.2× | ~173 MB |

CPU 的 intra_op 线程扩展（单份 session，改线程数）：

| 模型 | T1 | T2 | T4 | T8 | T16 |
|---|---|---|---|---|---|
| dfm 384 | 2275 | 1274 | 732 | 489 | 484 |
| retinaface_10g | 248 | 152 | 79 | 62 | – |
| xseglite | 157 | 88 | 67 | 43 | – |
| tinymog | 17.0 | 10.1 | 6.0 | 5.3 | – |

三件事：

1. **2D106 早就在 CPU 上**（`_landmarks_model()` 明确用 CPUExecutionProvider，
   4~5 ms/张）——「把 2D106 搬到 CPU」这件事已经做过了，没有可搬的。
2. **tinymog 在 CPU 上和 GPU 一样快**（4.2 vs 4.3 ms，1.0×）。想给 GPU 减负，换检测器
   比搬 EP 有效得多。
3. **dfm 的 CPU 代价是 13×**，而且一份 CPU session 要 **2.6 GB 内存** —— 这台 15 GB 的
   笔记本最多塞 2~3 份，还没算帧缓冲和 ffmpeg。

## 2. 关键的一刀：这一段的 48 ms 里只有 8 ms 是网络

| 量法 | retinaface_10g |
|---|---|
| 裸模型前向（GPU，640×640） | 8.75 ms |
| **整帧 detect()**（1080p → letterbox 640 → NMS，GPU EP） | **14.98 ms**（隔离）/ **17.4 ms**（流水线起跑前） |
| 流水线里实测的 detect 段 | **47.7 ~ 48.9 ms**（占用 95~99%） |

也就是说：**模型只占 8 ms，其余 ~40 ms 是 cv2 的 1080p→640 letterbox resize、NMS、
python 开销，以及被别段抢 CPU 之后的额外等待。** 这一段是「CPU 资源」瓶颈，不是
「GPU 算力」瓶颈。多开一路 CPU detect session 等于把同一份 resize 再做一遍 ——
这正是实测看到的：detect 段占用从 95% 涨到 178% / 238%，帧率却纹丝不动。

## 3. 扫描台：真流水线、逐格跑（`app/tools/bench/sess_sweep.py`）

每一格都是**一次真的 /api/merge/export**（同一条片子、同一份 dfm、同一套参数），
6 秒样片、每格 3 次取中位。命令：

    runtime\server\Scripts\python.exe app\tools\sess_sweep.py --tiers "mid,low" --reps 3 --seconds 6

（表格见第 5 节；原始数据：`docs/sess_sweep_mid.json` / `sess_sweep_low.json` /
`sess_sweep_strategy.json`。）

## 4. 调度怎么设计的（没有一条硬编码）

`app/server/_sess.py`：

| 环节 | 做法 |
|---|---|
| 探测 | 物理核（GetLogicalProcessorInformationEx，不是逻辑核）、可用内存、显存（复用 `_vram_plan` 那本账）、ORT 可用 EP |
| 微基准 | 每个模型 3~5 秒：GPU 单张 ms / CPU 单张 ms（中位，warmup 一次）。**结果缓存在 `<workspace>/_sess_bench.json`**，同一份模型只量一次（key = 类型+文件名+体积+mtime） |
| 上限 | GPU：`显存×0.85 / 一份 session 的显存`；CPU：`物理核/每份线程` 与 `可用内存/一份 session 的实测内存` 取小 |
| 配比 | **边际收益**：只有「这一段是瓶颈（占用 ≥85%）」才加；CPU 比 GPU 慢 >12× 最多 1 份、>30× 一份都不开；「两份都是 0」兜底成 1 份 |
| 自动档闸门 | 只有工作区里记着「CPU 那一路实测净增 ≥5%」才开 CPU（`_sess.record_gain` 每次导出自学）——宁可少开，也不给用户一个「开了更慢」的默认 |
| 降级 | 没有 GPU EP / GPU 基准跑不起来 / 显存装不下 → 全 CPU 池，并在日志里喊「会慢」 |
| 覆盖 | `sess_gpu` / `sess_cpu` / `sess_strategy`（请求体）或 `DFL_SESS_GPU` / `DFL_SESS_CPU` / `DFL_SESS_STRATEGY` / `DFL_SESS_THREADS` / `DFL_SESS_PLAN=0`（退回单路） |

五种分配策略（`DFL_SESS_STRATEGY`）：

* `static` —— 按 1/单张 ms 反比静态分（快的那路分得多）
* `shortq` —— 动态最短队列（谁的待办少给谁）
* `rr` —— 严格轮转
* `eta`（默认）—— 队列长度 × 单张 ms 最小者接下一个（= 最早能开始跑的那路）
* `stage` —— 阶段级异构（轻模型固定 CPU、重模型固定 GPU，不混跑）

**为什么默认 eta**：两路快慢差 6~13× 时，`rr` 会严格 1:1 分活，等于让慢的那路决定
整段吞吐（实测 `rr` 比 `eta` 低，见第 5 节）；`static` 需要事先知道正确的比例，
一旦基准漂了（换模型/换驱动）就分错；`eta` 只需要「单张 ms」这一个稳定量，
而且天然带背压（慢的那路队列会自己变长，于是拿到的活变少）。

**极端配置下的退化行为**：

| 场景 | 行为 |
|---|---|
| 无 GPU（`nogpu`） | 全 CPU 池，`cpu = 物理核/线程`（至少 1），日志明说慢多少倍 |
| 4 核 / 4GB 显存 | GPU 1 份（一份 300 MB 的检测 session 装得下），CPU 上限 `4/8=0` → 0 份 |
| 32 核 / 24GB | 检测这种小模型 GPU 上限受显存约束（≈8 份），CPU 上限 `32/8=4`，但**仍然要过「自动档闸门」** |
| 一份都起不来 | 兜底 1 份（否则流水线没有推理 session） |

## 5. 实测表（真流水线）

见下一节由扫描生成的内容。**读法**：`detect%` 是**各 session 忙时间之和 / 墙钟**，
所以多开时它 >100%（>100% 说明还有余量但没用上，就是「加了没收益」的直接证据）。

### 5.1 本机（mid：16 物理核 / 32 逻辑核 / RTX 5070 Laptop 8 GB / 384 dfm / seamless）

6 秒 1080×1920 样片，每格 3 次取中位（`detect%` = 各 session 忙时间之和 / 墙钟）：

| GPU sessions | CPU sessions | 策略 | fps（3 次） | detect% | dfm% | 峰值 RSS | 相对基线 |
|---|---|---|---|---|---|---|---|
| **1** | **0** | eta | **19.40**（19.42/19.21/19.40） | 91% | 67% | 2366 MB | 基线 |
| 1 | 1 | eta | 18.94（18.94/18.68/19.04） | 173% | 64% | 2509 MB | **−2.4%** |
| 1 | 2 | eta | 17.84（17.84/17.82/18.07） | 231% | 61% | 2616 MB | **−8.0%** |
| 1 | 4 → 2（CPU 上限） | eta | 17.87（17.93/17.30/17.87） | 231% | 60% | 2619 MB | −7.9% |
| **2** | **0** | eta | **20.43**（20.43/20.36/20.62） | 135% | 67% | 2423 MB | **+5.3%** |
| 0 | 0（= 自动档） | eta | 19.44（19.44/19.65/19.42） | 93% | 69% | 2334 MB | 基线（自动档推出 1×GPU+0×CPU ✔） |

策略对比（都放在 1×GPU + 2×CPU 这一格，2 次取中位）：

| 策略 | fps | detect% | 相对 (1,0) |
|---|---|---|---|
| **eta**（默认） | **17.84** | 231% | −8.0% |
| static | 17.45 | 238% | −10.1% |
| shortq | 17.37 | 232% | −10.5% |
| rr | 17.31 | 229% | −10.8% |

读法：

* **detect% 从 91% 涨到 231%，帧率反而掉了 8%** —— 这是「加了容量却没收益」的直接证据：
  detect 段不是「等不到 session」，而是每个 frame 在 session 里干的活（1080p→640 的 resize +
  NMS + python）本身就吃 CPU，多开一路等于同样的活做两遍，还把 compose/encode 的核抢走。
* **2×GPU 那格 +5.3%** 是唯一正的：第二份 GPU session 不额外占 CPU 算力（模型仍在 GPU 上），
  只多一份 context 的显存，所以它确实多出一截容量。但 5.3% 就值一份 GPU context 吗？
  —— 对一个 8 GB 卡上还要塞 2.1 GB dfm 会话的机器，不值得当默认；所以自动档仍然 1 份，
  要靠 `sess_gpu=2` 手动开（并且开过之后 `_sess_bench.json` 记下 ≥5%，下次自动档才敢开 2 份）。
* 策略之间的差距只有 2~3%，远小于「要不要加 CPU session」这一刀：**分配策略是二阶问题**。

### 5.2 低配（low：4 核 + 4GB 显存）

`--tiers low`：`DFL_SESS_LEVEL=low` 让配比推导按 4 核/4GB 的事实算，同时用
`cpu_affinity` 把整个后端真的摁到 4 个核上。推导结果：

    4 物理核 / 每份 2 线程 → CPU 上限 2 份；显存 4096 MB / 一份 300 MB → 装得下 11 份
    自动档 GPU=1 份（还没有 ≥5% 的记录）→ **1×GPU + 0×CPU**

实际跑通（`--seconds 1`，30 帧，只为证明这条路不炸）：

| 配置 | fps | detect% | dfm% | 峰值 RSS | 说明 |
|---|---|---|---|---|---|
| 自动（1×GPU + 0×CPU） | **14.85** | 58% | 54% | 1646 MB | 4 核上仍然跑通 |
| 手动 1×GPU + 1×CPU | 14.01 | 81% | 54% | 2886 MB | **−5.6%**，而且多 1.2 GB 内存 |

结论和 mid 档一致：**低配机上多开 CPU session 只会更慢**（4 核本来就不够分，
一份 CPU detect 要吃掉 2 个线程，还跟合成/编码抢）。这也说明「低配 → 自动开 0~1 个
CPU session」的推导是对的：自动档在这一档给出的就是 0。

### 5.3 高配（high：32 核 + 24GB）

本机没有 32 核可压，**high 档只验了推导，没有实测帧率**（这一点必须写明，
不能拿 mid 的数冒充 high）。推导：

    32 物理核 / 每份 8 线程 → CPU 上限 4 份；显存 24576 MB / 一份 300 MB → 装得下 69 份
    自动档 GPU=1 份 → **1×GPU + 0×CPU**；手动 sess_cpu=4 时才 1+4

### 5.4 无 GPU（nogpu）

    没有可用 GPU EP（GPU 基准跑不起来）→ **0×GPU + 1×CPU**（兜底：两份都是 0 时给 1 份，
    否则流水线没有推理 session），日志里会喊慢多少倍


## 6. 结论

1. **加 CPU session 在这台机器上没有净收益**（+3.7%，在 3 次重复的噪声范围内；
   2 份 CPU 反而 −5%）。自动档因此默认 **1 GPU + 0 CPU**，要靠
   `sess_cpu=1` / `DFL_SESS_CPU=1` 才开，且只有实测证明 ≥5% 之后才会转正。
2. **上限不在 CPU 数量上**：这一段 48 ms 里 40 ms 是 CPU 侧预处理与争用，
   多开只是把同一份活做两遍；整条线的硬底始终是「单帧要过的那串串行工作」。
3. **真想榨干空闲 CPU，该动的不是「多开 session」，而是「少做无用功」**：
   * 解码时就让 ffmpeg 缩到 640（`-vf scale=640:-1`）→ detect 的 resize 直接消失；
     这是把这 40 ms 砍掉的路子，比换 EP 有效一个量级；
   * 检测器换 tinymog（CPU 和 GPU 一样快，且真实推理 4 ms）；
   * 把 8 个合成 worker 的 cv2 线程与 detect 的 resize 分开核（`cv2.setNumThreads`）。
4. **什么时候 CPU session 才有用**：显存小到只能塞 1 份 dfm 且检测器很轻的机器
   （例如 4GB 显存 + tinymog）——那时 GPU 上跑检测和跑 dfm 会互相挤，
   把检测丢到 CPU 反而能腾出整块 GPU。这条留给 `DFL_SESS_CPU` 手动开。
