# 快速导出（fused）内存：量测、根因、修法

> 现象（用户实测，1080p / 1439 帧 / fused）：导出中「内存 13.0/15.2 GB（94%）、已提交
> 37/129 GB、GPU 7.0/8.0」，**导出结束后 RAM 仍然很高**，怀疑有东西没卸载。
>
> 结论先说：**不是 Python 对象泄漏**。13 GB 里本程序只占 3.2~5.4 GB，其余是桌面上的
> 别的进程；但确实有**两块该还的东西没还**（预览 worker 的会话、后端堆里已经释放的页），
> 现在都在收尾里显式还掉了，并把「导出前后 RSS 差」打进日志。

## 1. 怎么量的

`app/tools/export_mem_probe.py`（真后端 + 真视频 + 现成 dfm，全程 psutil）：

* 按角色分：**后端**（serve.py）、**预览 worker**（preview_worker_*.py）、**ffmpeg 子进程**；
* 每个角色记 **RSS（工作集＝任务管理器「内存」）/ private（提交）/ USS（独占）**；
* 采样点：导出前 / 导出中每 0.25 s（取峰值）/ 结束 +5 s / +30 s / +60 s；
* 系统口径：used / available / **commit** / nonpaged —— 用来分辨「真泄漏」和「已提交未驻留」。

跑法：

    runtime\server\Scripts\python.exe app\tools\export_mem_probe.py --full --runs 2

## 3. 谁在涨（有证据）

### 3.1 不是 list / dict / queue 无界增长

| 容器 | 上限 | 出处 |
|---|---|---|
| 逐帧日志 `_merge_job["log"]` | 4000 行 | `_VID_MAX_LOG` |
| 逐帧记录 `_merge_job["frames"]` | 20000 条 | `_VID_MAX_RECORDS` |
| 合成缓存 `_COMPOSE_CACHE` | 6 条（LRU） | `_COMPOSE_CACHE_MAX` |
| 预览命中 `_PREVIEW_HIT` | 1 条 | `clear()` 后单条写入 |
| 在飞帧数 | `BoundedSemaphore(budget)` | `sem = threading.BoundedSemaphore(budget)` |
| 段间队列 | q_dec/q_det/q_cmp/q_enc = 24，q_gpu = 64 | `_FUSED_QDEPTH` |
| 全景校验 | `live["peak"]` 实测 = 30（= 帧预算） | 日志「峰值在飞 30 帧」 |

两次导出的峰值**递减**、结束 60 s 后**完全不动** —— 这三条一起排除了「每帧漏一点」。

### 3.2 峰值是这四块叠出来的（1439 帧那次，3377 MB）

| 来源 | 量级 | 证据 |
|---|---|---|
| ORT 建 dfm 会话时 1567 MB 权重过一遍内存 | ~1.5 GB（一次性，建完就还） | 文件名给的 1567 MB；RSS 1064 → 3377 |
| 帧缓冲 30 帧 × 6.75 MB | 202 MB（设计内常驻） | `快速导出：显存预算 → 帧缓冲 30` |
| 检测/2D106/XSeg 会话 | ~0.5 GB | 预览后 1064 − 启动 586 |
| ffmpeg 编码子进程（x264 + 1080p 输入） | **~1.6 GB** | `ffmpeg RSS` 峰值 1616.9 |

### 3.3 结束后仍然占着的是三块

1. **预览 worker 的会话**（另一份，导出用不到）：实测 **1.27 GB 工作集 / 3.54 GB 提交 /
   2.3 GB 显存**。导出开始时 `_vram_reclaim` 会为了腾显存把它卸掉（日志：
   `回收预览模型 2128 MB`），但**显存宽松时它就不卸**，于是导出完一直占着。
   → 收尾里补了 `_free_preview_sessions()`（`DFL_FUSED_FREE_PREVIEW=0` 可保留）。
2. **后端堆里已经释放的页** ~1.0 GB：会话对象 `_DFM_SESS`/`_XSEG_SESS` 都清了、`gc` 也收了，
   但 NT 堆不会主动把页还给系统 → 任务管理器看起来就像没释放。
   → 收尾里 `SetProcessWorkingSetSize(-1,-1)`（`DFL_FUSED_TRIM_WS=0` 可关）。
3. **提交（private）比 RSS 高一个量级**：WDDM 上 cudaMalloc 的显存记在**进程提交**里，
   不进工作集。所以「已提交 37/129 GB」根本不是内存泄漏 —— 是显存 + 页面文件的账。

### 3.4 现场：13 GB 到底是谁的

同一时刻按进程量（修之前，用户报的那一版）：

| 进程 | RSS | 提交 |
|---|---|---|
| 后端 pythonw（serve.py） | 1905.8 | 4967.5 |
| 预览 worker | 1296.8 | 5608.2 |
| faceid 辅助 | 489.0 | 1631.0 |
| AI 客户端 ×2 | 2208.7 | 2864.8 |
| QQ ×3 | 812.1 | 1319.5 |
| explorer / electron / 壁纸 / Edge … | ~2000 | ~2600 |
| **全部 310 个进程合计** | **13181.7** | **30376.6** |

也就是说：本程序三个进程 3.7 GB，**剩下的 ~9.5 GB 是别人的**；导出峰值那 13.3 GB 是
「本程序 5.4 GB + 别人 8 GB」。这一条必须写进报告，不然「13 GB 全是 DFL」是错的口径。

## 4. 修法（都在 `app/server/routes_merge.py`）

| 位置 | 做了什么 | 为什么 |
|---|---|---|
| `_proc_mem_mb()` | psapi.GetProcessMemoryInfo → rss / private / peak | 和任务管理器同源，数字对得上 |
| `_mem_delta()` | 「导出前后」一行文本 | 用户要的那句话 |
| `_trim_ws()` | EmptyWorkingSet（默认开，`DFL_FUSED_TRIM_WS=0` 关） | 把已释放的页还给系统；**只降工作集** |
| `_free_preview_sessions()` | `_WORKER.unload("")`（worker 没起就不碰） | 那份会话是另开的，导出用不到 |
| `_fused_run` | 流水线前后 + 峰值 RSS 打进日志 | 峰值是谁的，一眼能看 |
| `_fused_worker` finally | ①卸 preview 会话 ②`gc.collect()`×2 ③工作集回收 ④打两行差值 | 成功/失败/取消都走同一条收尾 |

诚实口径：**工作集回收不降提交**。提交里 4.3 GB 是 ORT/CUDA context + arena，只有进程
退出才还 —— 日志里两个数都打，就是为了不让人把「工作集掉到 5 MB」当成「提交也还了」。

## 5. 验收

```
[PASS] 导出前后 RSS 差 ≤ 300 MB  · 实际 -1.4 MB（后端 -1.4 / worker +0.0）
[PASS] 第二次峰值不高于第一次  · 峰值 RSS #1=4994.2 MB · #2=3529.4 MB
```

## 6. 还没做的（下一刀）

* **ffmpeg 编码子进程 1.6 GB**：`-threads` / `-x264-params rc-lookahead=` 都能压，代价是编码变慢。
  （这次没动：它是峰值里第二大的，也不是泄漏。）
* `-dml` 无关。**真正能砍峰值的是「解码时就缩到 640」**（见 sess_pool 文档里 detect 的数据）。
