# 28 · 像素对拍的口径：什么能比、什么不能比

> 一句话口径：**fused 整片对拍不是逐位可复现的 —— 同一份代码跑两遍，150 帧里只有 62 帧逐字节相同。**
> 所以「整片 PNG 对拍 = 0 LSB」**不能**拿来验收 fused 的输出，更不能拿它证明某次改动「无损」。
> 证据、成因、以及该用哪种对拍方式，都写在这篇里。

---

## 1. 现象：同实现两遍，只有 62/150 帧相同

2026-11，dfm 出参那单（commit `20b3d73`）顺手量到的。同一段片（1080×1920 · 150 帧 · 416 dfm · bf16w），
**同一个实现**（出参搬法 `DFL_DFM_OUT=legacy`）跑两遍，逐帧逐像素比 PNG：

| 对比 | 逐字节相同的帧 | 单点最大差 | 最差帧的 mean |
|---|---|---|---|
| legacy 跑第 1 遍 vs 第 2 遍（**同一实现**） | **62 / 150** | **35 LSB** | 0.0045 |
| legacy vs merged（**不同实现**） | 67 / 150 | 32 LSB | 0.0042 |
| legacy vs merged，mode B（串行，确定性） | **60 / 60** | **0** | 0 |

第三行是关键：**换成确定性模式之后，两种实现逐字节相同**。
也就是说前两行的差异不是「谁算错了」，而是「这两遍跑的根本不是同一个计算」。

## 2. 成因:攒批组成随队列时序变 → bf16 卷积归约顺序变

fused（mode C）的 dfm 是**攒批**跑的：GPU 线程从 `q_gpu` 里能拿几张就攒几张（上限 8），
拿多少取决于那一刻队列里已经有多少张脸 —— 也就是**解码/检测/对齐的速度**。

同一次改动前后两次运行实测：平均 3.33 张/次 vs 3.57 张/次，直方图也不同
（`{1:2, 2:1, 3:1, 4:5, 5:5, 6:2, 7:2, 8:9}` 这类分布每次都在动）。

批大小一变，cuDNN/cuBLAS 选的 kernel 与归约顺序就变；bf16 的累加精度只有 ~3 位十进制，
顺序一变，最后几位就变 —— 这是**同一个模型、同一份权重、同一份输入**的正常数值行为，
不是 bug。它也是 `TOL_MEAN = 1.0`（fused vs 分段）那条注释里说的同一件事。

三条推论：

1. **mode C 的产物不是「确定性函数」**。它不是随机数，但它是「攒批时序的函数」。
2. 只要整片里有一帧的批组成变了，**逐帧**就可能差几十个 LSB（单点最大 35 LSB 见过）。
3. 这种差异**不会**被下游的 `np.clip(x*255,0,255).astype(u8)` 吃掉 —— 它比 1 个 u8 还大。

## 3. 该用哪种对拍

按「你改的是什么」选，别一律上整片对拍：

| 改的是什么 | 正确的对拍 | 硬指标 |
|---|---|---|
| **搬运/管线**（D2H、pinned、线程、队列），前向不动 | 同进程、同一份 device 出参，两种搬法各搬一次 | `max|diff| = 0`（`dfm_out_bench.py --ab` 的「逐位对拍」表） |
| **前向后端/精度**（dtype、EP、图折叠） | 确定性模式跑端到端：`fused_pipeline_bench.py --modes B`（串行），或固定 `--batch` 且单线程 | 逐字节相同 |
| **合成/遮罩**（CPU 代码，跟 GPU 批无关） | 同参数两次跑，或直接比中间数组 | 逐字节相同 |
| 非要在 mode C 上量 | **只能用统计口径**：≥2 遍**同实现**先量噪声底，再拿改动的均值跟噪声底比 | mean LSB 落在噪声底内 |

第 1 行是最常用的：**改搬运不需要跑整片**。`app/tools/bench/dfm_out_bench.py --ab` 就是为它写的
——同一份 `ys`、两种实现、`max|diff| = 0`、非零像素 0；再加一条确定性端到端（mode B 60 帧 60/60）就够了。

## 4. 反面教材（今天真发生过）

- 拿 `C_out` 的 150 张 PNG 比 legacy vs merged，看到 67/150 不同、max 32 LSB，差点判「改动改了像素」。
  再补一组 **legacy vs legacy**（同实现两遍）→ 62/150、max 35 LSB —— 噪声底比信号还大，
  这条对拍**从一开始就不该做**。
- 同理，`fused_export_accept` 里「fused vs 分段」对拍用的是 `TOL_MEAN = 1.0` 而不是 0：
  两条路的攒批天然不同（fused 攒 8、分段逐张/批 4），恒为 0 只是当年切到 TRT 定档的巧合。

## 5. 顺带：这条也解释了「单次采样比阈值」为什么危险

同一个「检测档」开关，`per_stage_ms.detect` 今天量到的绝对值：

```
默认档（retinaface_10g） 24.2 / 35.5 / 35.7 / 37.5 / 38.0 / 38.1 / 38.6 / 38.8 ms
fast  （tinymog）         7.2 /  7.6 /  8.0 / 19.2 / 20.6 / 22.1 / 22.4 / 22.7 / 23.0 / 24.0 / 24.1 ms
```

同一档位跨运行能差 **3.3×**（fast 的 7.6 vs 24.1），而 `per_stage_ms` 本身就是整段 139 帧的
均值（帧间误差 <1%）—— 所以差异全在**整轮之间**。
凡是「拿两个整轮的标量比值卡阈值」的断言，都必须先取多轮中位（`fused_export_accept.py` 的
`DET_ROUNDS = 3`），否则它测的是机器状态，不是被测的开关。
