## 1 图捕获：成功

| 项 | 值 |

| 模型 | 416（156 个真算子）· 384（183 个） |
| 捕获档 | b1 / b2 / b4 / b8 各一份，在 **dfm 自己的流**（`DfmTorch.gstream`）上捕 |
| 捕获耗时 | 416：848 / 128 / 242 / 489 ms（b1 首捕含 cuDNN 选算法；捕获前在同一流上热 3 次） |

| 失败回退 | 捕获异常 → `★ CUDA Graph 捕获失败 batch=N（原因）→ 回退 eager`，该档不再重试；batch 不在捕获档 → 打一次日志走 eager；NCHW/CPU 会话 → 打一次日志 |
| 开关 | `DFL_DFM_GRAPH=0`（默认关）· `DFL_DFM_GRAPH_B=1,2,4,8` · `DFL_DFM_GRAPH_WARM=3` |

每次 replay 的提交环只剩：`np.copyto`（主机）→ 1 次 H2D → **1 次 cudaGraphLaunch** → 3 次 D2H → 1 次流同步
（出参的 bf16→fp32 cast 也录进图，省掉每帧 3 次提交 + 3 次分配）。
profiler 记到的 CPU 侧事件（`opcount.py`；kineto 在本机拿不到 CUPTI，驱动调用不计数）：
**eager 1271 → 图 45（−96.5%）**。eager 那 1271 里排前的是 `as_strided 185 · slice 123 · narrow 120 ·
view 85 · reshape 84 · empty 72` —— 156 个真算子展开后的 aten/dispatch 事件，正是「生产态每次提交都要抢一次 GIL」的那批。

## 2 逐位对拍：max|diff| = 0（不是 ≤1 LSB）

分布（单位 u8 LSB）：**100% 落在 =0 这一桶**（`==0` 的计数 = 张量元素总数，`(0,1e-5)` 起全为 0）。
bf16 那 1 LSB 的额度**没用上**：同一串算子、同一 device 输入、权重地址不变，图重放就是同一个计算。

5 条自检（`stress.py`，全过）：uint8 入参 0 差 · 连放 20 次（中间掺 eager）0 差 ·
**`torch.cuda.empty_cache()` 之后 replay 仍 0 差**（图的私有池不会被 empty_cache 收走 —— 真正的风险点，专测）·
图入口对错形状抛 `ValueError` · 未捕获档（b2）回退 eager 且出正确形状。

生产态对拍（最硬的一条）：`_fused_run` 150 帧，**off×3 + on×3 六次导出，mp4 md5 全部 =
`C0DC8D2F0824B37E234E1FE49508612C`**；8 写线程那组 off×2 + on×2 也全等（`9287B768…`）；
40 帧那组同样两臂同 md5。**逐帧攒批组合、对齐、合成、编码全链一致。**

**稳态结论（两会话共 10 个臂-轮，去掉前 ~12 帧）**：

`compose` 100ms/帧、`xseg` 7.2 → 11.5ms（图不再占默认流，xseg 与它重叠了）、dfm 车道占用 62% → 47%。
把编码线程 3 → 8（`ab_w8.json`，100 帧×2 轮）：off 13.99 / 18.05 → on 20.16 / 20.37，**暖对 +12.9%**。

## 4 隔离态 vs 生产态：同一件事的两个口径

`iso.py`，147 次 b1 调用 ×3 轮取中位（提交环 = t_fwd；call = 整次调用；gpu = CUDA event 的 kernel 时间）：

| 争用档 | 臂 | 提交环 ms | 一次调用 ms | GPU ms |
|---|---|---|---|---|
| 静默（无邻居） | eager | **6.36**（6.65/6.36/5.03） | 19.83 | 18.70 |
| 静默 | 图 | **0.33**（0.33/0.33/0.22） | 19.59 | 18.35 |
| +8 条 numpy（放 GIL） | eager | **8.35**（8.69/8.35/7.16） | 21.04 | 19.72 |
| +8 条 numpy | 图 | **0.42** | 20.44 | 19.16 |
| +1 条纯 Python（抢 GIL） | eager | **5227**（5288/5154/5227） | 5519 | 5243 |
| +1 条纯 Python | 图 | **46.5**（46.1/46.9/46.5） | 279 | 31.6 |

这张表就是这单的全部逻辑：

* **静默态图几乎不省钱**（19.83 → 19.59，−0.2ms）：没有 GIL 争用时那 156 次提交只要 6ms，且与 GPU 重叠 ——
  这正是之前「cudagraphs +0~2.8%，不值得」的来源。
* **争用一上来两个口径就分叉**：生产态 eager 23.5 / 图 1.06，**贵出来的 16.9ms 几乎全是 GIL 税，
  图臂只剩 0.7ms 税**（静默 6.36 → 生产 23.5 = +17.1）。
* 最极端的 +1 纯 Python 忙线程：5227 → 46.5ms（**113×**）。156 次抢锁 vs 5 次抢锁，量级差就在这。

## 5 结论

* **提交环：生产 23.5 → 1.06ms（−95%），静默 6.4 → 0.33ms。** dfm 一次调用 28.3 → 20.1ms，
  GPU 窗口 23.9 → 14.9（省的是「GPU 等提交」，不是 kernel）。
* **e2e：dfm 车道上限从 28.3 抬到 20.1ms/帧；这条片子 fps 中位 +6%（7 对 6 胜、暖对 +5.1/+6.1/−0.6），
  因为编码已是墙（enc_wait 99%）——编码腿松开时（8 写线程）暖对 +12.9%。** cycle p95 −5%、σ −24%，抖动更小。
* 数值逐位不变（`max|diff|=0`；六次 150 帧导出同一个 md5）。默认仍 `DFL_DFM_GRAPH=0`；打开后
  加载多花约 0.45s（只捕 b1）/ 约 1.7s（捕 1,2,4,8），显存 +14MB / +88MB。
* 残余：图臂一次调用只剩 45 个 CPU 事件，其中 6 个是 `_outs` 的 detach/copy、4 个 `aten::to` ——
  把 3 次 D2H 也录进图（静态 pinned 出参）能再砍一半，代价是出参生命周期要从「一次调用一条」改成
  「谁拿到谁拷走」，这单不动它。
* 下一步该动的不是 dfm，是编码那条腿（`enc_wait` 99%）与 compose（100ms/帧）：它们才是现在的帧率上限。
