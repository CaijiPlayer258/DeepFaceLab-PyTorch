# 四臂：compose 在哪儿算 × 用哪个编码器（CPU 侧还剩多少空间）

> 目的：把整条线从 21~30 帧/秒 往 50 推之前，先量清楚「合成搬到 GPU」和「编码换 NVENC」
> 各自到底动了谁的核、谁的等待。**默认值一个都没改**，四臂全靠 env / 请求体切。
>
> 台架：`app/tools/bench/arm_bench.py`（12 次导出 + 6 次热身，四臂按轮交替）
> 原始数据：`%TEMP%\dfl_arm_bench\arm_ab.json`（每轮的 fps / 全 profile / 四项 wait /
> 进程树核数拆分 / NVML 采样 / 成片 md5）

## 0 口径

| 项 | 值 |

| 设置 | seamless + mt + mask_mode 6 + mask_blur 4（erode 0） |
| 模型 | 阿証証証証-416（torch · bf16w），检测器不点名（默认 tinymog） |

| 工作区 | 沙箱 `%TEMP%\dfl_arm_bench\ws`（model/_engines 目录联接；仓库 workspace 只读） |

| 交替 | 每轮 A C（x264 进程）→ B D（nvenc 进程），共 3 轮；每个进程先跑 1 次热身丢弃 |

## 1 判据（先写，避免事后圆）

1. **编码器变了 → 成片不可比**：A/C 是 x264，B/D 是 nvenc（按成片里的 `x264 - core` SEI 判，
   `<成片>.log` 的命令行被 `_vid_log` 截到 300 字符，看不见 `-c:v`）。只比 **A vs C**、**B vs D**。
2. **md5 不是跨轮不变量**：A 三轮三个 md5（`6c8aea…/bbdd01…/8d0587…`），B 两轮一个、一轮另一个 ——
   dfm 攒批时序不同，像素本来就差几 LSB（见 `fused_export_accept` 的 TOL_MEAN 注释）。
   所以「换编码器 md5 必变」这条判据在本轮**没有判别力**；C/D 反而是三轮同一个 md5（GPU 合成那条路更稳）。
3. **同组内比 fps**，跨组只看方向。

## 3 机制

* **A 的墙是 GPU 车道，不是 x264**：dfm 23.2 + u8 7.1 + xseg 9.6 = **39.9 ms/帧 串在一条线程上**
  （`_gpu()` 里 dfm→D2H/u8→xseg 顺序执行，batch 1），40/49.5 = 81% 忙；x264 只让写者堵 6.7ms（14%）。
  GPU SM 只有 42.5% —— 那 57% 的空转里，一半是这条车道的 **CPU 部分**（凑批数组 + D2H + u8 量化），
  一半是每次前向的提交/同步（一帧 ~40 个 kernel launch，见 docs/26 §5.4）。
* **B 把 CPU 还给了 GPU 车道**：编码 ffmpeg 4.85 → 1.10 核，省下的 3.75 核没进"空闲"，
  被 python 侧吃掉（13.6 → 16.6 核）：detect 26.3 → 14.3、compose 251 → 175、u8 7.1 → 4.3。
  于是 GPU 车道 39.9 → 34.4 ms/帧，fps +15.9%（20.2 → 23.4）。**这不是"只降占用"**。
* **C/D 的墙变成了写者**：write 6.7 → 53.7ms（90% 占用），dec_wait 15% → 72%（帧预算被写者占着），
  上游全空转（decode 21%、detect 20%、dfm 34%、compose 37%）。原因不是"合成在算"，而是
  **GPU 合成在 WDDM 上花 CPU**：python 进程 13.6 → 19.4 核，而 4 条合成线程自己只占 1.5 核（37%×4），
  多出来的 5.75 核花在提交/同步与 torch 的线程池上；同一时刻 x264 少了 1.4 核（4.85 → 3.45）就排不空管道。
  这和 docs/26 §5.3 量到的是同一件事（CPU 合成 7.3~8.3 核 → GPU 合成 10.2~13.1 核）。
* **GPU 合成没有"把 8 条线程腾出来"**：compose 那 3.9 核（5.4 → 1.5）确实还回去了，
  但 decode 的 ffmpeg 反而**更少**（1.63 → 0.92 核），decode 车道每帧 25.5 → 12.5ms 是
  "不再被 cv2 的 300 条线程挤"的**去虚高**，不是"拿到了更多核"。

## 4 建议

| 旋钮 | 结论 | 代价 |
|---|---|---|
| `DFL_COMPOSE_GPU`（含 `DFL_COMPOSE_GPU_SEAMLESS`） | **保持 0**（别默认开）。同一台机上 C 比 A 慢 26%、D 比 B 慢 17%，且把写者/背压变成新墙 | 0；开了要多付 ~5.75 核 |
| `DFL_FUSED_ENCODER=nvenc-h264` | **值得给用户选，但默认仍 x264**：+15.9%（23.4 vs 20.2），体积 −5%（5.28 vs 5.53MB），代价是换 md5、码率曲线、需 NVENC 卡 | 成片不可比；功耗峰 65.4W（贴着 65W 墙） |

**下一个该动哪：GPU 车道（dfm→u8→xseg 一条线程 34.4ms/frame，其中 ~9ms 是 CPU：凑批数组 + D2H + u8）**，
其次是 decode 车道（25.0ms/frame 单线程，50 帧/秒需要 ≤20ms）。这两条不动，B 的天花板就是 29 帧/秒。

## 6 顺带发现（不是本轮结论，但下次会咬人）

* `_pred_pick_batch` 的阶梯实测**同一个模型会在 1 和 8 之间跳**（本轮 A 有一轮是 batch 8、两轮是 1；
  B 反过来）。日志会说"B8 比最优贵 8% → 按实测用 1 张"。这是逐轮的噪声源（±1~2 fps），
  不是四臂之间的差异来源（两种 batch 下 A vs B、A vs C 的差值方向一致）。
* 采样器全程在**另一个进程**里（NVML 10Hz + psutil 进程树），本轮没有出现 `enc_unlock.md` 里
  那种"探针把 21.8 压到 18.4"的现象：四臂的 A 中位 20.2 与无探针历史值同量级。
