# 一个 dfm 到底吃掉了多少 GPU？（RTX 5070 Laptop 8GB · 2026-11-16 · 只测不改代码）

**判定：b1 就把整张卡吃满了 —— 95% busy、贴着 65W 功耗墙、再开第二条流换不来吞吐。原来那两个数不是同一状态下量的，不能拿来证明「攒批便宜 29%」。**

## 口径
一格一个进程（server venv / torch 2.9.1 / bf16w + CUDA Graph，生产默认）。每格预热 6 次，再跑 K 次**背靠背**调用（≈2.4s 窗口）×7 rep 取中位；NVML 50ms 采样只取窗口内样本。416 b1 另复测 2 个进程（21 次中位，±1%）。ms/张 = run() 墙钟/张（含 H2D+D2H）；另记 CUDA event 的**前向真忙**时间。输入固定种子噪声。

## 三个判断
**① b1 占用 94.8%(416) / 95.6%(384)，不是 <70%，而且不是错觉。** 同一模型再开一条**独立 CUDA 流 + 独立权重**：一次调用 19.8→39.2ms（两张流严格对半分），聚合 49~51 与单跑 48~52 完全重叠 —— 是同一块算力在轮流用，没有新增产能。三张流直接退化。没装 ncu 量不到 warp occupancy；但 util 95% + 扩容零增量，两个代理指标同向：b1 已占住整张卡的时间片。
**② b8 = 97.3%（两张模型），SM 不再涨；攒批只在 384 上有意义。** 416：19.80→20.22（−2%，噪声）—— b1 已经吃满，攒批纯亏一帧延迟。384：21.87→17.58（−20%），GPU 真忙 20.75→16.98 ms/张 —— 省的是 GPU 时间，不是主机时间。机制看得到：b1 每张都要把 783MB 权重整走一遍，b8 摊薄 8 倍（同族证据：416 用 fp32 权重那档 b1 22.65 → bf16w 19.80）。
**③ 反推上限**：416 1000/19.80 = **50.5 fps**（b1）vs 2000/39.83 = **50.2 fps**（跨帧 2 张攒一批）→ **−0.6%，白付一帧延迟**。384：**45.7** vs **52.8 fps → +15.6%**（b8 更狠：56.9）。这就是「跨帧攒批」的全部理论收益：416 上没有，384 上 16%。

## 关于那两个互相矛盾的数
416 b1 在本机构建上换三种状态都量过：bf16w+graph **19.80**、bf16w eager **20.45**、bf16（fp32 权重）**22.65**；对应 b8 = 20.22 / 20.92。**28.3 在任何干净状态下都复现不出来** —— 它是「机器上另有 GPU 任务 + 流水线里的 b1」那次（旧报告 §11 自己写了这点），而 20.0 是独占机器的 b8。跨状态相减得出的 −29% 不成立；真实值：416 约 0%，384 约 −20%。

## 降频与环境
当前功耗墙 **65.12W**（默认 50W，上限 115W），dfm 全程 66~77W 均值（峰 83~105W），throttle reason **每次采样都带 sw_power_cap**；SM 跑 2.15~2.28GHz vs boost 3.09GHz。**没有随时序降频**：各 rep 时钟不下降（min 1.35~1.75GHz 是瞬时采样）。绝对值都压在功耗墙下：比较结论成立，绝对值偏保守。机器也不静默：后台 idle 18~19W / 8~9% util，所有 util 都含这 8%。

**结论：一个 dfm b1 吃掉整张卡的吞吐（95% busy、贴着功耗墙、第二条流 +1.6%），只剩同一条流里的攒批能挤一点 —— 416 挤不出（0%），384 挤 16~20%（付一帧延迟）。再挂第二个模型 = 把第一个的 fps 砍半。**
