# 18 · 合成器只算 ROI（整帧 float32 遮罩/合成 → 脸所在那一块）

> 这一页记的是「合成器单帧 330ms」里那一段**纯内存带宽**的活：
> 遮罩反贴、两次合成、两次 clip、出图 u8、遮罩阈值/包围盒 —— 原来都在整帧
> 1920×1080 的 float32 上来回搬（一帧 25MB，十来个算子 = 每帧搬 200MB+）。
> 实测遮罩支撑只占整帧 **2.2%**、包围盒 **3.1%**，遮罩外一个像素都不会变。
> 改成「只算 ROI」之后：**MergeMaskedFace 288.2 → 137.1 ms（2.10x）**，
> 项目导出 **1×1 6.29 → 11.82 帧/秒（1.88x）**、**2×4 11.47 → 21.02 帧/秒（1.83x）**
> （`proj_pool_accept` 那套沙箱里是 1×1 3.84 → 8.21、2×4 7.28 → 12.62），
> 且**与整帧版逐位一致**（进程内同 session 对拍 mean=0 / max=0）。
> 开关：`DFL_MERGE_ROI=0` 退回整帧版（原代码原样留着，是参考实现）。

## 二、ROI 版做了什么

`MergeMaskedFace` 的标准模式加了一条快路 `_compose_roi_standard()`，区域有两层：

* **roi** = 遮罩支撑（`img_face_mask_full > 0`）的包围盒 —— 实测 3.1% 面积。
  **只有这里会改像素**，出图与遮罩都只在这块里算，其余直接沿原帧。
* **work** = 脸画布四边形（`face_mat` / `face_output_mat` 两张）在原帧里的并集
  **+ 8px** —— 实测 13.5%。它比 roi 大，因为它同时是
  「把 out_img 反变换回画布」那个 warp 的**取样源**：取样点周围 ±2px 也得是真的。

逐处对应（左侧整帧版的行、右侧 ROI 版怎么算）：

| 整帧版 | ROI 版 |
|---|---|
| `argwhere(mask>=0.1)` 定区域 | 在 work 里扫（work 外遮罩恒为 0，等价） |
| 遮罩 `clip` + `<1/255→0` | 只对 work 这一块做（work 外本来就是 0） |
| seamless 二值遮罩 | 只对 roi 做；`boundingRect` 算出来加回 roi 原点，`center` 与整帧版逐字节相同 |
| `seamlessClone` | **仍是整帧输入/输出**（见第五节），src 用 `frame.copy()` 填 work、dst 直接用原帧（原来的 `astype(uint8)` 只是一份内容相同的拷贝） |
| 合成①/② | 在 work / roi 的**视图**上做同样的表达式 |
| 后处理回 warp | 取样源是 work 那块 out_img（整帧形状的缓冲，惰性填） |
| 出图 u8 | `frame.copy()` + roi 内 `clip(out*255).astype(u8)` |
| final_mask | `zeros` + roi 内换算（盒外恒为 0） |

## 三、逐位一致的依据（四条，都是「按定义」，不是「差不多」）

1. **遮罩支撑外合成式退化成恒等**：`img_bgr*(1-0) + x*0` 在 float32 下就是
   `img_bgr` 本身；而 `u8 → f32(/255) → *255 → u8` 这一趟对 0..255 **全部 256 个值
   逐位无损**（实测 256/256 相同），所以盒外直接沿用原帧像素 = 整帧算出来的结果。
2. **切片是同一块内存的视图**：乘加/clip/阈值在切片上算与整帧算同 dtype、同运算
   顺序 → 逐位相同。
3. **seamlessClone 盒外不改像素**：它的 Poisson 解只读遮罩包围盒那一块，盒外输出
   **恒等于 dst**（实测盒外 max|diff| = 0）。所以只需要「盒内 + 它的依赖区」是真的。
4. **两个反贴 warp 仍按整帧坐标做**：把 ROI 平移折进矩阵平移项会让坐标的定点舍入
   （1/32 px）变位 —— 实测 44%~79% 的像素差 1e-5 量级（见第五节）。只有 3.7ms，
   不值得为它冒逐位不一致的险：切成切片、值是同一份。

## 四、两条被数据否掉的做法（别照抄别的仓库）

1. **「把 ROI 平移折进仿射矩阵的平移项、只 warp ROI」不逐位一致。**
   `warpAffine` 把坐标按 1/32 px 定点化，平移项换个算法写法就会在边界上多/少一个
   1/32 px，插值权重跟着变：实测遮罩反贴 44% 像素、脸反贴 79% 像素差
   **max 8.0e-5 / 1.8e-5（float 域）**。折算到 u8 会有零星 ±1 LSB —— 逐位对拍
   这条就过不去。省下来的只有 3.7ms，所以**不做**。
2. **「把 seamlessClone 裁成 ROI 再算」不逐位一致。**
   它内部确实只解遮罩包围盒，但**输入尺寸会改边界条件**：裁成小图实测差
   **max 3~7 LSB、10%~50% 像素**（pad=4 最好也只有 max 3）。
   而且裁了也不快：整帧输入 23.4ms vs ROI 输入 23.2~24.8ms —— 它的耗时跟整帧尺寸
   无关，只跟遮罩盒有关。所以**不裁**，只省掉它那三张整帧 uint8 的生成（12ms → 1ms）。

## 五、对拍与回归

```
runtime\server\Scripts\python.exe app\tools\roi_parity_accept.py            # 进程内逐位对拍（快，无需后端）
runtime\server\Scripts\python.exe app\tools\roi_export_accept.py            # 真后端端到端 + 帧率 + 续跑（慢）
```

`roi_parity_accept` 的口径：同一个进程、同一个 session、**同一份前向输出**
（dfm/xseg 结果按帧号缓存，两侧吃同一份）+ 同一个 `np.random` 状态（`color_transfer_idt`
里有一句没播种的 `np.random.normal`，不固定种子比的就是随机方向）：

| 项 | 内容 | 结果 |
|---|---|---|
| A | 真项目 89 帧 × 项目参数 | mean 0 / max 0 / 遮罩 0，89/89 帧都走了 ROI 快路 |
| B | 42 组参数 × 2 帧（mode × mask_mode(0-9) × ct(0-10) × erode/blur × 运动模糊/锐化 × 超分 × output_face_scale × face_type） | 全部 0 |
| C | 六宫格 `capture`（预览那条路） | 6/6 面板逐位相同 |
| D | 320×240 / 1081×1921 / 脸一半在画外 / 脸整个在画外 / 遮罩全零 | 全部 0 |
| E | 单帧墙钟（前向缓存清空，两档都真跑模型） | 288.2 → 137.1 ms |
| F | 面积 | mask>0 **2.24%** · 包围盒 **3.12%** · 工作区 **13.49%** |

端到端（`roi_export_accept`，240 帧 PNG 项目、JPEG q92 落盘）：

240 帧，连跑三轮（帧速抖动 ~5%，给的是三轮的区间）：

| 档位 | ROI=0 | ROI=1 | 倍数 | swap p50 |
|---|---|---|---|---|
| 1×1 | 6.13 ~ 6.29 帧/秒 | **11.82 ~ 12.24 帧/秒** | 1.88 ~ 2.00x | 293~300 → 136~145 ms |
| 2×4（默认） | 11.40 ~ 11.71 帧/秒 | **21.02 ~ 21.77 帧/秒** | 1.82 ~ 1.91x | 1115~1208 → 531~555 ms |

**跨进程比对的口径要说清楚**：两个 ROI 设置是两个后端进程，各加载一次模型，
cuDNN 选核/累加顺序会让少数帧差 1~2 LSB —— 这是**改造前就有的噪声**，不是 ROI 引入的：

| 比对 | 逐字节相同 | mean | max |
|---|---|---|---|
| 1×1：ROI=0 vs ROI=1 | 204~206/240 | 0.000039~0.000041 LSB | 4~5 |
| 2×4：ROI=0 vs ROI=1 | 178~189/240 | 0.000063~0.000084 LSB | 8 |
| **负控：2×4 同参数两次运行（ROI 都是 1）** | **186~187/240** | **0.000063~0.000070 LSB** | **8** |
| 旧代码里 1×1 vs 2×4（档位差，与 ROI 无关） | 200/240 | 0.00024 LSB | 4 |

也就是说 ROI 前后的差异**小于「同一份代码跑两次」的噪声地板**，且差异区域集中在
脸（dfm 输出的末位差被 seamless 的 Poisson 放大），不是 ROI 的边缘。
「逐位一致」的严格证明在 `roi_parity_accept`（进程内）——那里是 0。

回归（三套全过）：

| 回归 | 结果 |
|---|---|
| `stage6_accept` | PASS 64 · FAIL 0（63.7s） |
| `fused_export_accept` | PASS 64 · FAIL 0（107.1s，18.58 帧/秒） |
| `proj_pool_accept` | 19 项通过 / 0 失败（扫描表 + C 段逐像素对拍 + D 段续跑） |

`proj_pool_accept` 自己的扫描表就是最直观的前后对照（同一个脚本、同一台机器）：

| 档位 | 改造前（commit 6a2d639 记录） | 现在 | 倍数 |
|---|---|---|---|
| 1×1 | 3.84 帧/秒 | **8.21** | 2.14x |
| 1×4 | 6.34 | **11.66** | 1.84x |
| 2×2 | 6.88 | **13.61** | 1.98x |
| 2×4 | 7.28 | **12.62** | 1.73x |
| 2×8 / 3×4 | 1.5~1.9（显存 spill） | 1.86（同样 spill） | — |

**顺带一个结论**：每帧的 CPU 活少了一半之后，**默认 2×4 已经不是最优**了 ——
现在 2×2（13.61）比 2×4（12.62）快 8%，1×4（11.66）也追得很近。线程越多，
「4 个线程抢同一台的 CPU」这件事越吃亏。要不要把默认 worker×batch 改成 2×2
是另一件事（默认值有显存和回归口径的连带影响），这里先只记录实测。

## 六、开关与不走 ROI 的情况

* `DFL_MERGE_ROI=0` 退回整帧版；默认开。
* 这几项**不走 ROI**（`_roi_gate`）：`raw-rgb` / `raw-predict`（另一套输出）、
  `image_denoise_power` / `bicubic_degrade_power` / `color_degrade_power` 非 0
  （它们按定义要读/改整帧 img_bgr）、帧不是 uint8、脸画布占了大半帧（没有收益）、
  脸整个在帧外。
* 遮罩支撑太小（`min(bbox) < 4`）：整帧版在这一点上原来会抛
  `UnboundLocalError`（`out_img` 没赋值）被外层 `except` 兜住、原样返回帧；
  ROI 版把同一个结果直接返回（少一条 traceback 噪音），像素一样。
* `ROI_STATS`（模块级计数器）留着排障：`frames / work_none / big /
  roi_taken / roi_false`（多线程下数值可能偏小，只用来回答「走没走快点」）。

## 七、还能往哪走

* **色彩迁移（18ms，416 画布）**：`match_tone_np` 的均值/方差是**整张画布**的加权
  统计量，压到遮罩包围盒会改数值（六阶段的 `_merge_compose._match_tone_roi` 就是
  这么干的，注释里写着「差别只在 float32 求和顺序」——即**不是**逐位一致）。
  要动它得先决定这条线允许不允许末位差；现在是 101ms 里最大的一块。
* **临时缓冲复用**：ROI 版每帧还要 `np.empty_like` 两三块整帧 f32（25MB/块），
  实测「每次新分配 3 块」33.8ms vs「线程内复用」28.0ms —— **约 5.7ms/帧**，
  代价是每线程多 75MB 常驻。按需再上。
