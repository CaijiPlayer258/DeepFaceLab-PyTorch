# 09 · 推理性能实测手册

> 本机实测：RTX 5070 Laptop 8GB · TRT 10.13.3.9 · Windows
> 所有数字都来自真机跑出来的结果，不是估算。**「试过但无效」那一节同样是资产**——
> 它记录的是已经花过时间验证过的死路，别重复走。

---

## 一页速览

### 最终采用的方案

| 环节 | 方案 | 实测 |
|---|---|---|
| 遮罩推理（XSegLite 256²） | **INT8 引擎** | 2.04 → **0.751 ms**（2.7×） |
| 遮罩预处理 | `cv2.dnn.blobFromImage` | 1.387 → **1.067 ms** |
| 遮罩批量 | 线程池 **8** | 40,646 张 ≈ **1.1 分钟** |
| 检测（TinyMog 640²） | CUDA Graph + GPU 预处理 | 3.91 → **2.98 ms/帧** |
| 特征点（2D106 192²） | CUDA Graph（自动生效） | **0.711 ms/脸** |
| 视频解码（1080p） | `cv2.VideoCapture` | **3.78 ms/帧** |
| warp / JPEG 编码 | `warpAffine` / `imencode` | 0.12 / 0.30 ms/脸 |

**1080p 每帧合计 ≈ 11 ms → 2 分钟视频约 40 秒。**

### 一句话原理

> **浅网络（launch 密集）用 CUDA Graph，深网络（算力密集）用 INT8。**
> 用错方向会得到「优化了但更慢」的结果——三条实测都验证了这一点。

## 一、三颗模型，三种最优解

| 模型 | 体积 | 瓶颈 | INT8 | CUDA Graph | 最终选择 |
|---|---|---|---|---|---|
| XSegLite 遮罩 | 19 MB | 算力（29 Conv + 4 上采样） | **2.7×** ✅ | 无效（更慢 15%） | INT8 |
| TinyMog 检测 | 0.3 MB | launch（网络极浅） | 1.22× | **2.0×** ✅ | Graph |
| 2D106 特征点 | 4.8 MB | launch（全连接头） | 1.05× ❌ | **3.6×** ✅ | Graph |

### 质量代价：只有遮罩可以接受

| 模型 | 质量影响 | 结论 |
|---|---|---|
| 遮罩 | IoU 0.970 / 二值一致 99.1%，差异只在轮廓 **1~2px**，且**单向内收** | 训练软遮罩可用 |
| 特征点 | 关键点平均漂移 **2.26 px**（最大 9.33） | **否决**——对齐和遮罩定位都会偏 |
| 检测 | INT8 未验证框质量 | 未采用 |

> 为什么遮罩能忍、特征点不能忍：遮罩是**软标签**，边缘 1px 抖动会被训练平滑；
> 关键点是**硬坐标**，2px 漂移会直接传给后续对齐矩阵。

## 二、遮罩应用：40,646 张的完整链路

| 环节 | 每张 | 说明 |
|---|---|---|
| read meta | 0.237 ms | 读 DFLJPG 的 APP15 段 |
| imread | 1.057 ms | 线程池并行 |
| **mask（INT8）** | 1.067 ms | 含 resize + 转置 + 推理 + 回读 |
| encode | 0.210 ms | |
| write | 0.697 ms | 线程池并行 |
| **合计（8 线程）** | **1.658 ms** | **≈ 1.1 分钟** |

**起点对比**：bf16 引擎 + numpy 预处理 + 4 线程 ≈ 3.6 ms/张 → 2.4 分钟。**整体快 2.2 倍。**

### 线程数扫描（240 张/轮）

| 线程 | 4 | 6 | **8** | 12 |
|---|---|---|---|---|
| ms/张 | 2.057 | 1.752 | **1.658** | 1.731 |

8 是拐点：GPU 推理是**加锁串行**的（一个引擎一个 context），再多线程只是在抢锁。

## 三、提取器分段（1080p，1 脸/帧）

| 环节 | 耗时 | 占比 |
|---|---|---|
| decode | 6.32 ms/帧 | 41% |
| detect | 6.61 ms/帧 | 43% |
| landmark | 1.93 ms/脸 | 13% |
| warp | 0.12 ms/脸 | 1% |
| encode | 0.30 ms/脸 | 2% |

**解码 + 检测 = 84%**。模型侧只占小头——所以「优化提取器」≈「优化解码和检测的像素处理」。

## 四、试过但无效的方案（别再试）

### 1. 逐层混合精度（bf16 权重 + OBEY_PRECISION_CONSTRAINTS）

| 项 | 结果 |
|---|---|
| 权重体积 | 19.0 MB → 9.5 MB（确实减半） |
| 引擎速度 | 2.114 → **2.435 ms（更慢 15%）** |
| 质量 | 概率最大差 0.999 ❌ |

**原因**：ONNX 各层声明 FP32，开 `obey_precision_constraints` 等于**禁止** TRT 降精度，
还额外插入转换 kernel。

### 2. 全局 BF16（权重 FP32，只开 BF16 标志）

引擎 33.2 → 15.0 MB；速度只快 10%（2.148 → 1.920），但概率最大差 **1.00**（像素 0↔1 翻转）。不划算。

### 3. CUDA Graph 用在 XSeg

2.191 → **2.523 ms（更慢）**。54 个卷积已把 GPU 队列填满，没有 launch 空隙可省。

### 4. NMS 换 `cv2.dnn.NMSBoxes`

3.91 → 3.96 ms，**无收益**。一帧只有几十个候选框，手写 NMS 不是瓶颈。

### 5. ffmpeg 管道解码

| 方式 | ms/帧 |
|---|---|
| **cv2.VideoCapture** | **3.78** |
| ffmpeg 管道（1080p 原始） | 83.59 |
| ffmpeg 管道 + 缩到 960×540 | 22.98 |
| ffmpeg 管道 + 缩到 640×360 | 11.01 |

**瓶颈是管道传输**：1080p 一帧 BGR = 6.2 MB，Python 读字节流直接卡在内存拷贝上。

### 6. ffmpeg CUDA 硬解（`h264_cuvid`）

ffmpeg 本身支持（`-hwaccels` 列出 cuda / dxva2 / qsv / d3d11va / d3d12va），
但解出的帧在显存里，交给 OpenCV/numpy 必须 `hwdownload` 回 CPU——
**6MB 的 D2H 拷贝比软件解码更贵**，实测吐不出可用帧。

> 只有「检测 → 对齐 → 编码」全部留在 GPU 时硬解才有意义。当前是 TRT + numpy 混合，不成立。

### 7. 应用侧多线程解码

| 线程 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| ms/帧 | 6.03 | 5.58 | 8.65 | 13.32 |

每线程各开一份 `VideoCapture` 还要 seek，代价超过并行收益；H.264 本身有帧间依赖。

## 五、复现要点

1. **测遮罩不要跑原目录**：先把文件复制到 `workspace/_mask_test`，避免覆盖已有遮罩；
2. **纯 GPU 时间**用 `torch.cuda.Event` 包住 `execute_async_v3`，别用 `time.perf_counter` 包 `sess.run`（后者含 H2D/D2H 与同步）；
3. **等价性验证**：改实现后除了看速度，还要比输出（框坐标 / 遮罩 IoU），
   本次检测器 GPU 预处理的验证结果是**框坐标差 0.0000 px**；
4. 校准集用**真实对齐脸**（本次 200 张），合成数据会让 INT8 的 scale 偏。
