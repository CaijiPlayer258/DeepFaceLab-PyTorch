# 20 · 项目导出的自适应档位（同条件 A/B + 实测规则）

> 这一页回答两件事：
> ① 用户说「项目导出怎么还更慢了」—— **同一个模型**下到底快了还是慢了（同条件 A/B）；
> ② 项目模式原来只有「静态规则 + 显存闸门」，现在补上**实测驱动的自适应**（量 → 选 → 跑起来再复查）。
>
> 机器：RTX 5070 Laptop **8GB** · R9 8940HX · 32GB · Windows
> 素材：同一份 **120 帧**真项目（`000029.jpg`~`000148.jpg` · 1080×1920 · aligned 120 张）
> 参数：seamless + mt + XSegLite（mask_mode=8 / erode 0 / blur 4）· 检测器 tinymog · quality 92
> 每格 **3 次取中位**，格子交错跑（第 2 轮倒序、第 3 轮打散），不换机器、不换项目。
> 显存 = `nvidia-smi` **整卡**占用；**本次开工前桌面已经占了 1592 MB / 8151 MB**（dwm 600 +
> 用户的后端 312 + QQ/wallpaper/overlay 等）—— 历史页面里的 800MB 空载基线是在这些没开时量的，
> 所以**绝对峰值不要和历史页逐 MB 对**；能对的是「同一个模型、同一台机器、同一份项目」的 A/B。

---

## 一、结论（先给答案）

1. **同一个 384 模型：改后比改前快 3.07 倍，没有变慢。**
   `2×2` = **3.49 帧/秒**（95.2% 显存，swap p50 952ms）→ `1×4` = **10.73 帧/秒**（88.6%，367ms）。
2. **同一个 416 模型：这条代码路径没改它的默认值，也没有退化。**
   今天的 `2×2` 实测 **13.39 帧/秒**，历史页面记的 13.42 是同一个数（±0.3%）；
   只有退到 1 worker 才掉到 10.70 —— **416 上 2 worker 仍然是对的**。
3. **用户拿 13.42 和 10.0 比是跨模型比较，无意义。**
   13.42 = 416（**514MB / 134.8M 参数 / 输入 416**）+ 2 worker；
   10.0 = 384（**1567MB / 410.8M 参数 / 输入 384**）+ 1 worker。权重差 3.0 倍、参数差 3.0 倍。

## 二、同条件 A/B（完整表）

| # | 模型 | 请求 workers×batch | **实际生效** | 帧/秒（3 次） | 中位 | 显存峰（整卡） | swap p50 |
|---|---|---|---|---|---|---|---|
| A | **384** 张元英（1.53GB / 410.8M / 384） | **1×4（当前默认）** | 1×4 | 10.89 / 10.68 / 10.73 | **10.73** | 7202~7230 MB（**88.6%**） | 367 ms |
| B | 384 同上 | 2×2（改前默认） | **1×2**（预算砍成 1 个） | 9.81 / 9.84 / 9.88 | 9.84 | 5658~5716 MB（70.0%） | 211 ms |
| C | 384 同上 | 1×2 | 1×2 | 9.67 / 9.71 / 9.95 | 9.71 | 5598~5660 MB（69.3%） | 213 ms |
| **D** | **384 同上** | **2×2 强制（= 改前默认真跑）** | **2×2** | 3.49 / 2.89 / 4.59 | **3.49** | 7757~7764 MB（**95.2%**） | **952 ms** |
| E | **416** 阿証（0.51GB / 134.8M / 416） | **2×2（当前默认）** | **1×2**（预算砍成 1 个） | 9.67 / 9.67 / 9.75 | 9.67 | 4562~4641 MB（56.0%） | 215 ms |
| F | 416 同上 | 1×4 | 1×4 | 10.70 / 10.61 / 10.85 | 10.70 | 5159~6243 MB（75.8%） | 364 ms |
| **G** | **416 同上** | **2×2 强制（= 当前默认真跑）** | **2×2** | 14.81 / 13.39 / 12.39 | **13.39** | 6393~6957 MB（**79.8%**） | 294 ms |

读法（三句话）：

* **384 这一列：D 就是「改前」。** `2×2` 把两个 1.5GB 会话同时压在卡上 → 整卡 95.2%、
  swap p50 952ms、帧速 3.49（和 19-SPEED.md 记的 3.61 / 4.79 同一个坑）。
  **A（1×4）= 10.73，快 3.07 倍，显存还少 540MB。** 「384 的默认从 2 worker 改成 1 worker」这一刀是对的。
* **416 这一列：G 就是「现在」= 13.39 帧/秒 / 79.8%**，与历史 13.42 一致；F（1 worker）只有 10.70
  → **416 上少一个 worker 白丢 25%**，所以 416 继续 2×2。
* **B、E 是今天新发现的问题**：请求 2 个 worker 却被预算**砍成 1 个**（桌面占 1.6GB），
  于是 416 的默认档在用户机器上实际只跑到 9.67 —— 用户看到的「慢」有一部分来自这里。

## 三、「以前 13.42 / 现在 10.0」为什么不能直接比

| 维度 | 13.42 那一次 | 现在 10.0 |
|---|---|---|
| 模型 | 阿証…-416.dfm | 张元英.dfm |
| 权重 | **514 MB** | **1567 MB**（3.0×） |
| 参数量 | **134.8 M** | **410.8 M**（3.0×） |
| 输入边长 | 416 | 384（像素少 15%，但参数多 3 倍） |
| 档位 | 2 worker × 2 线程（4 帧在飞） | 1 worker × 4 线程（4 帧在飞） |

两档「在飞帧数」都是 4，差的是**权重**和**参数量**。同一台机器、同一份项目：

* 384 的天花板 = `4 / swap_p50 ≈ 10.5~11.1 帧/秒`（一份会话 + 4 线程），10.0 已经压在这条线上；
* 416 的权重只有 1/3，2 份会话在 8GB 卡上还留 20% 余量，所以能到 13.4。

**跨模型比帧速没有意义**：换的是权重体量和参数量，要比就得同一个 dfm 比。

---

## 四、今天真正的问题：2 worker 档被预算砍了

今天的桌面占 **1.6GB**。预算（`_vram_plan`）按「一份会话峰值 + 批台阶」估 416 的 `2×2`
需要 **5781MB / 可用 5812MB** —— 差 30MB → **降成 1 个 worker**；而真跑起来整卡只到
**6503MB（程序 4906MB）**，明明是够的（79.8%）。

**估算把实测的 2×2 判死了**（保守 600MB）。后果：用户机器上 416 的默认档形同虚设（实际 1×2 = 9.67），
而且光看静态规则永远发现不了 —— 因为规则里的数字是估的。

所以这一轮把项目模式改成**实测驱动**：量 → 选 → 跑起来再复查；并且**实测在换页线以内时，
可以覆盖预算的削减**（有日志、有 status、有降档兜底）。

## 五、自适应档位（这一轮新加的）

### 5.1 量什么（`_proj_run._calibrate`）

起导出前用 **16 帧**（`_projplan.SAMPLE_FRAMES`）把候选档位**真跑一遍**；帧速按**稳态**算（每路第一批丢掉，算后面几批的墙钟）—— 2 worker 那档头两批还在热 arena，12 帧全算会把 13.4 量成 10.0，直接选错档：

* 帧不随便挑：先 `_prep` 探一遍，只收**真能换脸**的帧（本片有 16 帧「有对齐脸但检测器没检出」，
  拿它们标定会量到「原样搬运」的 110 帧/秒，那是假的）；
* 每档记三样：**帧速**（这 12 帧的墙钟）、**整卡显存峰**（150ms 采一次 nvidia-smi）、
  **worker 单帧 swap p50**；
* 预筛：估算整卡占用超过**换页线 92%** 的档不量（真装不下由 `add_one` 失败兜住，当场 close）；
* 量完写 `<workspace>/_proj_bench.json`，`key = 模型名|体积|mtime`（换权重自动失效）。

### 5.2 怎么选（`_projplan.choose`，没有写死的数字）

| 规则 | 内容 |
|---|---|
| ① 显存 | 优先在**实测峰 ≤ 85%** 的档里选帧速最高的（85% 是用户口径的目标） |
| ①b 换页线 | 85% 内最快那档如果比「85%~92%」那档**慢 10% 以上**，选后者并写明理由（今天是 1×4：89% 但快 11%）；> 92% 直接出局 |
| ② 争用 | **2 worker 的 swap p50 > 1.4 × 1 worker 的最好值，并且帧速也没快过 5%** → 判为争用/换页，不用 2 worker。两个条件都要：2 份会话共用一块 GPU，单帧 swap 本来就会涨（那是排队）。416 实测 2×2 = 335ms vs 1×2 220ms（1.52×）却快 25% —— 只看 swap 会把这档更快的那档否掉；真换页是「swap 涨、帧速塌」（384 的 2×2：4.5×、3.49 帧/秒） |
| ③ 相邻档 | 某档比低一档（在飞帧数更少）**慢 10% 以上** → 跳过（噪音/换页，不是配置） |
| ④ 没实测 | 保守默认（≥1GB → 1×4，≤600MB → 2×2）；第一单跑完把实测写回去，之后不再花这 12 帧 |

日志一行（`server.log` / `job.log` / status 都有）：

    [project] 基准：1x2=9.7 fps 213ms / 1x4=10.7 fps 367ms（取 1x4，显存 89%）
    [project] 基准：1x2=8.7 fps 208ms / 1x4=10.0 fps 362ms / 2x2✗=4.8 fps 366ms（取 1x4，显存 77%）

`✗` = 出局；括号里那句是选中理由（含 swap 对照与显存百分比）。

### 5.3 跑起来之后（`_tick → _adapt_check`）

每 `DFL_PROJ_ADAPT_EVERY`（默认 **200**）帧复查一次：

* **降档**：显存 > 88%，或 swap p50 比开跑基线恶化 > 50% → 先**线程 −1**；线程已是 1 就
  **关掉一个空闲 worker**（`pool.retire()` 只关正在空闲的那个，绝不打断在飞的批）；
* **升档**：显存 < 70% 且 GPU 利用率 < 50%（喂不饱）且线程还没到实测最优 → 线程 +1（最多 2 次）；
* 每次升降都写 `log` + `status.adaptive.events`（帧号 / 原因 / 当时档位）。
* 两个旋钮：`DFL_PROJ_ADAPT_EVERY`（复查间隔，默认 200 帧）、`DFL_PROJ_ADAPT_PCT`（降档阈值，默认 88%）。
* 判定看**当前占用**（`samp.now`），不看历史峰值 —— 峰是单调的，拿它判会从 4 线程一路
  棘轮到 1（今天 384 就在 88.6%，这个 bug 是实测抓出来的）。

### 5.4 手动优先

请求体或环境变量（`DFL_PROJ_WORKERS` / `DFL_PROJ_BATCH`）给了值 → `src="off"`，
一句都不改，只按显存预算削减（并照旧提示「装不下，已减到 N」）。

## 六、验收

### 6.1 自适应（本轮实测）

| 验收项 | 结果 |
|---|---|
| **384 冷启动**（无缓存 → 现场标定 16 帧；2×2 估算超换页线，直接不量） | `src=bench`，标定 `1x2=8.8 fps 195ms / 1x4=9.3 fps 362ms` → **选 1×4（84~85%）**；正式跑 **10.12 帧/秒** |
| **384 热启动**（缓存命中，不再标定） | `src=cache`，仍然 1×4，**10.16 帧/秒** —— 和冷启动只差 0.4%，说明标定那 3 秒没有摊进帧速 |
| **384 手动 workers=1 batch=2** | `src=off`，档位就是 1×2，日志「手动指定 workers/batch → 不改（只按显存预算削减）」 |
| **416 冷启动** | 标定 `1x2=9.4 fps 198ms / 1x4=10.4 fps 354ms / 2x2=11.8 fps 317ms` → **选 2×2（76%）**；正式跑 **14.27 帧/秒**（workers=2 batch=2，无降级告警） |
| **416 热启动** | `src=cache` → 2×2，12.67 帧/秒（同一档，波动是机器抖动，不是档位变化） |
| **预算 vs 实测** | 这一单预算是「只装得下 1 个 worker」，实测 2×2 整卡 76% ≤ 换页线 92% → **覆盖削减**（日志一行写明）；这正是第四节那个 bug 的修法 |
| **像素一致** | 384 1×4 vs 1×2：mean **0.0001** LSB / max 8；384 冷 vs 热：**0.00015** / max 5；416 冷 vs 热：**0.00032** / max 7（都是老代码同样的 CUDA 浮点噪声地板，≤0.5 LSB） |
| **静态默认档不回归** | `app/tools/proj_default_accept.py`（该测试把 `DFL_PROJ_BENCH=0`，验的还是「按权重」那条老规则）：**PASS 28 · FAIL 0**（80.9s；A 段 384 1×4 = 8.65 帧/秒 / 本程序 6437MB = 79%，B 段 416 2×2 = 10.93 / 73.1%，C 段手动 2→1 降级+提示，D 段逐像素 mean 0.0015 LSB） |
| **运行中降档** | `DFL_PROJ_ADAPT_EVERY=20` + `DFL_PROJ_ADAPT_PCT=80`（把阈值压到 80% 好让它真触发）跑 384：第 40/60/80 帧各降一次，**4→3→2→1 线程**，每次都写 `[project] 自适应降档：显存 82% > 80% → 线程 3` 与 `status.adaptive.events`；120 帧照样跑完、0 失败（降档只关空闲 worker / 改批大小，不打断在飞的批） |

### 6.2 一句话对照：自适应到底改了用户什么

| 场景（同一台机器、同一份 120 帧项目） | 改之前 | 改之后（自适应） |
|---|---|---|
| 384 · 桌面干净 | 2×2 = 3.49（95% 换页） | **1×4 = 10.7**（85%） |
| 416 · 桌面干净 | 2×2 = 13.39 | 2×2 = 13.39（不变，它本来就是最优） |
| 416 · 桌面占 1.6GB | 2×2 被预算砍成 1×2 = **9.67** | 实测 2×2 76% → **14.27**（+47%） |
| 显存紧张到 2×2 真不装 | 硬砍/换页 | 标定时直接量不到 2×2（`add_one` 失败）→ 自动退 1×4，并写日志 |

## 七、限制（说清楚，别当没有）

1. **预算估算仍偏保守**：416 的 `2×2` 估 5781MB / 实测 4906MB（多算的约 900MB ≈ 批台阶
   与已含批的会话峰值被记了两遍）。自适应路径用**实测覆盖**它（416 今天 9.67 → 14.27），
   但 `_vram_plan` 那条静态账没动 —— 动它要连带改 `16-VRAM-BUDGET` 那一整套验收。
2. **标定只用来排序**：16 帧量到的绝对帧速比 120 帧真跑低 ~17%（416 `2×2` 11.8 vs 14.27），
   因为 6 轮还填不满流水线。所以它只进「谁比谁快」的比较，不进任何对外报数。
3. **整卡百分比会随桌面漂**：今天基线 1592MB，A 段有一轮整卡到 93.8%（程序仍只 79%）。
   看「程序占多少」比看「整卡多少」稳；两栏都留在 status 里。
4. 缓存文件是 `<workspace>/_proj_bench.json`（只留最近 12 条模型记录）；换权重 / mtime 变了
   自动失效，想强制重量就删掉它。
