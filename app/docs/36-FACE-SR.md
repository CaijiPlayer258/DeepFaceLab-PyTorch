# 36 · 人脸超分（GPEN-BFR-512）

> 合成器的**可选**后处理：把合成后的脸做一次盲修复，补高频细节。
> 默认关（`DFL_SR=off`）—— 关着的时候一个像素都不动（mode B 的 30 帧 md5 与基线逐字节相同，已验证）。

## 为什么是 GPEN 不是 GFPGAN

| | GPEN-BFR-512 | GFPGAN v1.4 |
|---|---|---|
| 身份保持 | **强**（更保守，不乱编细节） | 弱（会往"它见过的脸"偏） |
| 观感 | 偏软 | 更好看，但会磨皮/塑料 |
| 我们的输入 | **干净但低分辨率**（换脸结果） | 同左 —— 但 GFPGAN 会过度补细节 |

换脸最不能接受的失败是「被改成别人」，GPEN 的失败模式（偏软）可以用混合强度补回来，
GFPGAN 的失败模式补不回来。所以选 GPEN。

## 在哪做（这一条最影响画质）

```
❌ 芯片上做：芯片 224~416，模型要 512 → 先放大再缩回 = 一次多余重采样（先糊再加锐）
✅ 帧空间做：合成完成后，取该脸的 ROI 原生像素 → 512 → 推理 → 缩回 → 按遮罩 alpha 混回
```

实现：`backend_merge/compose.py::_apply_sr_layers()`，在 `compose_frame` 与
`compose_aligned_frame` 的**最后一次回 u8 之前**逐脸调用。所以视频模式与项目模式都吃得到。

## 开关

| env | 值 | 说明 |
|---|---|---|
| `DFL_SR` | `off`(默认) / `low` / `mid` / `high` | 混合强度 0 / 0.35 / 0.6 / 1.0 |
| `DFL_SR_BACKEND` | `auto`(默认) / `trt` / `onnx` | auto = 有 engine 用 engine，否则 onnxruntime |
| `DFL_SR_SIZE` | `256`(默认) / `512` | 工作分辨率；模型与引擎都跟着它选（**256 单次 9.5ms，512 单次 57ms**） |
| `DFL_SR_MODEL` | 路径 | 覆盖模型路径；不给就按 size 选 `weights/gpen_bfr_{256,512}.onnx` |

**强度不是 1.0**：GPEN 会把脸往训练分布拉，100% 替换会把目标人的特征洗掉。
默认 `mid=0.6`，要"只补一点"就用 `low`。

## 引擎（本机实测）

```bat
runtime\server\Scripts\python.exe app\server\backend_models\trt_build.py ^
  --onnx weights\gpen_bfr_512.onnx ^
  --out weights\_engine\gpen_bfr_512.1200.bf16.engine --name gpen --bf16
```

- 构建 **135.8 s**，产物 **161.5 MB**（源 onnx 271 MB）。
- 推理 **57.0 ms/次**（RTX 5070 Laptop 8GB @60W，bf16 + CUDA Graph）。
- onnxruntime 在这台机器上会退回 CPU（cuDNN 9 不匹配）→ **1.16 s/次**，不要用 onnx 后端。

## 代价（实测，别按想象）

**两个尺寸都量过（同一台 RTX 5070 Laptop 8GB @60W、bf16 TRT、单脸）：**

| 模型 | 引擎 | 单次 | 真实流水线 C（60 帧） |
|---|---|---|---|
| **GPEN-BFR-256**（默认） | 45.1 MB / 编 95.8s | **9.5 ms** | 78.5 ms/帧 · **12.73 帧/秒**（关着 15.49） |
| GPEN-BFR-512 | 161.5 MB / 编 135.8s | 57.0 ms | 502 ms/帧 · **1.99 帧/秒** |

**默认用 256**：只掉 18%（15.49 → 12.73）。512 版慢 7.8 倍，只适合「不在乎时间的一单」——
所以 `DFL_SR_SIZE=512` 是个显式选择，不是默认。

### 早期那组数据（512，mode B）

| 场景 | 关 | 开（mid） |
|---|---|---|
| mode B（串行基准，12 帧） | 191 ms/帧 | 290 ms/帧 |

**C 那一行是硬事实：这台机器上 GPEN-512 bf16 单次 57ms，而整帧预算只有 64ms，
GPU 又已经 95% 占用 —— 插进去就是 7.8 倍变慢。**

原因不是代码写得差，是三件事叠加：
1. GPEN-512 本身重（StyleGAN2 系，512×512 上十几层卷积）；
2. 本机 GPU 被 **60W 功耗墙**卡住（SM 2.2GHz）；
3. SR 会话必须独占串行（8 条合成线程不能并发 run 同一个引擎），于是它变成整条流水线的串行段。

**已试过并否决的做法**：
- `use_graph=True`：每条线程各捕一次图（40~80ms/次），跑流水线直接卡死 → 改 False；
- `own_stream=True` + event 同步：和其它 lane 抢设备，反而更慢。

## 结论（2026-11 复核）

- **256 是实用档**：9.5ms/次，整条线只掉 18%（15.49 → 12.73 帧/秒）。已经够用。
- **512 是质量档**：57ms/次，掉到 1.99 帧/秒，只有"这一单可以等"时才选。
- int8 暂不做：要先准备校准集（`trt_build.py` 目前只有 `--bf16`），而 256 的 9.5ms 已经够。
- 如果哪天要更快：把 SR 挪到独立 lane 与 dfm 重叠（要重排流水线，收益上限是 9.5ms/帧）。

**当前状态：默认关（`DFL_SR=off`），开起来默认走 256。** 关着时 mode B 30 帧 md5 与基线逐字节相同。
