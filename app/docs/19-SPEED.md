# 19 · 速度报告（ONNX only）

> 口径先说死：**dfm 只走 onnxruntime（CUDA EP），不编 TRT 引擎、不降精度**。
> 本页所有数字来自同一个脚本、同一份 JSON（`D:\MyProject\_speed41\speed.json`），
> 每格跑 3 次取中位；格子之间的差异只来自配置，不来自"换了一次机器"。
>
> 机器：RTX 5070 Laptop **8GB** · R9 8940HX · 32GB · Windows
> 素材：`workspace/9月29日 (5).mp4`（1080×1920 · 30 fps · **1439 帧** · 47.967 s）
> 模型：`张元英.dfm` —— **384**，dfm 里写死 `in_face=[N,384,384,3]`（1.5 GB）
> 参数：seamless + mt + XSegLite（`mask_mode=8` / erode 0 / blur 4），检测器 tinymog
> 占用口径：显存 = `nvidia-smi` 的**整卡**占用（空载基线 800 MB / 8151 MB，
> 所以 4483 MB ≈ 本程序 3.7 GB）；CPU = 整棵进程树、归一成**占全机 16 核**的百分比；
> RSS = 流水线自己打的"峰值 RSS"（0.5 s 采样的进程树峰值也一并给出，会漏峰）。

## 二、为什么"片段之间 fps 不同"

一部片子里并不是每帧都有人脸。本片 **1221 / 1439 帧有人脸（84.9%）**，其余 218 帧
（15.1%）一张脸都没有 —— 这些帧只做「解码 → 检测 → 原样编码」，换脸那三段整段跳过。
逐段每帧 ms（同一套参数、同一台机器，只是窗口不同）：

| 段（ms/帧） | 有人脸 | 无人脸 | 差 |
|---|---|---|---|
| decode | 12.4 | 22.7 | +10.3（无人脸那段码率低、CPU 更空闲，反而被单线程解码卡住） |
| detect | 23.3 | 8.3 | −15.0（没有框要 NMS / 关键点） |
| align（68 点 + 仿射） | 19.5 | **0.2** | −19.3 |
| **dfm（换脸）** | **28.9** | **0.66** | −28.2 |
| **xseg（遮罩）** | **9.0** | **0.5** | −8.5 |
| **compose（融合）** | **85.2** | **0.47** | −84.7 |
| encode（PNG） | 76.3 | 47.5 | −28.8（平帧压得更狠） |
| **合计** | **47.9 ms/帧 → 20.9 帧/秒** | **32.1 ms/帧 → 31.2 帧/秒** | 1.49× |

所以：**人脸密集段 ≈ 21 帧/秒，空镜/静止段 ≈ 31 帧/秒，整片 22.3 是加权结果**。
GPU 利用率也跟着掉（51% → 26%）—— 无人脸帧几乎不碰 GPU，瓶颈回到单线程解码和 PNG 编码。

> 复现这段结论用的是**区间导出**（`start_frame/end_frame`），不是估算：
> 无人脸窗口 1281–1400、有人脸窗口 29–148，两个窗口都由项目 `aligned/` 的逐帧对齐结果
> 判定（有对齐脸 = 有人脸帧），跑完再看 `per_stage_ms` 是否真的塌下去 ——
> 实测 dfm 28.9 → 0.66 ms，证明窗口确实是纯无人脸。

## 三、检测器对照：+21.7% 这件事到底是不是真的

同段 120 帧、同参数、只换检测器（**其余一个字没动**）：

| 检测器 | 帧/秒 | detect ms/帧 | 墙钟 | 相对 |
|---|---|---|---|---|
| retinaface_10g | 18.26 | **47.8** | 13.6 s | 基线 |
| tinymog | 20.83 | **24.0** | 12.7 s | **+14.1%** |

> 表里的 47.8 / 24.0 是「这一段摊到每帧的墙钟」；日志里零图空载测的前向是
> **retinaface 12.69 ms / tinymog 7.84 ms**（`检测器 tinymog（…）· 1080p 单帧 7.84 ms =
> letterbox 1.05 + 前向 6.17 + NMS/解码 0.06`）。差值不是算错：流水线里所有 GPU 活
> （detect / dfm / xseg）共用一条流，满载时每帧都要排队，**排队时间算在段里**。
> 这也正是「换检测器的绝对收益 ≈ 每帧 24 ms，百分比看其余段占比」的原因。

**方向和历史结论一致（检测单帧 48 → 24 ms，翻倍），倍数这一轮是 +14.1%，不是 +21.7%。**
原因不是"那个收益是假的"，而是**分母不一样**：历史那次（`64a11c5` 提交里记的
23.26 → 28.30 帧/秒）跑的是 416 dfm + 另一段片子，检测在整条流水线里占的份额更大；
这一轮用的是 384 的 1.5 GB 模型，**compose（85 ms/8 线程）和 encode（76 ms/3 线程）
比检测更吃时间**，同样的 23.8 ms 省下来，摊到总帧时间上就只有 14%。

一句话：**换检测器的绝对收益是"每帧省 24 ms"，百分比随其余各段的占比浮动** ——
其余段越轻越接近 +21.7%，其余段越重（比如 384 大模型 + seamless 融合）越接近 +14%。

## 四、项目导出（2×2 默认档）：显存贴着上限那一档

| 项 | 值 |
|---|---|
| 帧/秒 | **3.61**（3.00 / 3.61 / 3.78，抖动大） |
| 显存峰值 | **7749 MB / 8151 MB（95%）** |
| worker 单帧 swap p50 | 458 / 1334 / 1135 ms（中位 **1135 ms**） |
| 墙钟 | 49.8 s / 120 帧 |
| GPU / CPU | 47.3% / 10.1% |

2 个 worker 各持一份 **1.5 GB 的 384 dfm**，光权重就 3 GB，加上 ORT arena、批 2 的中间张量
和落盘缓冲，整卡被顶到 95%。WDDM 在显存将满时会把页换出去，于是 worker 的换脸时间从
458 ms 一路抖到 1334 ms —— **这一档的瓶颈不是算力，是显存**。

* 对比历史：`17-PROJ-BATCH.md` 里 2×2 = 13.42 帧/秒用的是 416 的 **0.5 GB** 模型；
  换到 1.5 GB 的 384，同一档位直接掉到 3.6。所以"2×2 是默认档"这条结论对**模型体量**敏感，
  不是对所有模型都成立。
* 这一档还出现 16/120 帧「有对齐脸但（默认档检测器）没检出人脸 → 按原帧落盘」，
  那是检测档位差异，不影响上面的吞吐口径（原样帧更便宜，等于把数字**高估**了一点点）。

| 项 | 值 |
|---|---|
| 端到端 | 120 帧 / 22.7 s = **5.29 帧/秒** |
| 六段 | frames → faces → pred → mask → merge → encode，每段独立产物 |
| 显存峰值 | 4615 MB |

## 七、复现

```
# 全跑（每格 3 次取中位）
runtime\server\Scripts\python.exe app\tools\speed_bench.py

# 只跑某一组
runtime\server\Scripts\python.exe app\tools\speed_bench.py --scenes fused-full --reps 1
runtime\server\Scripts\python.exe app\tools\speed_bench.py --scenes det-cmp --reps 3

# 原始数据（每次的 per_stage_ms / 日志行都在里面）
runtime\server\Scripts\python.exe app\tools\speed_bench.py --json D:\MyProject\_speed41\speed.json
```

脚本自己起 `app/serve.py`（`DFL_WORKSPACE=_speed41\ws`）、自己采样（nvidia-smi + psutil
进程树）、自己收尾 kill 进程树；跑完打一张总表并把每次的 `per_stage_ms` / 日志行全写进 JSON。

> 换模型：`DFL_SPEED_BOX`（工作区根）、`DFL_SPEED_XSEG`（xseglite.onnx）、
> `DFL_SPEED_PROJECT`（算"有人脸帧占比"用的 DFL 项目）三个环境变量，
> 再把脚本里的 `DFM` 常量改成模型名即可。
